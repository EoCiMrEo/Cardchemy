# Proposed source input repair after the complete contract audit

Date: 2026-10-01 (America/Chicago). **Recommendation, not approved or
implemented.** The [completed audit](2026-10-01-source-contract-audit-result.md)
and five-page diagnostic are finished. This note asks for a concrete next
decision; it does not reopen a consumed pilot or change release thresholds.

## Evidence defining the repair

All 66/264 public cases remain, with 109 jointly useful page/cue pairs.
Five useful references are not sufficiently represented in actual wire input.
An independent original-page diagnosis found four missing visual learning
relations, no omitted additional native text, and one uncertain attribution.
Every one of those five supplied contexts already contains its complete
native page text. Increasing the same-page text window therefore adds no
material in these cases. All 54 conclusive positive questions still have at
least one useful observable text source; this is a candidate/input bound,
not measured model performance.

The known input omissions already consume the complete exact-cardinality miss
allowance in the two- and three-useful strata. A text-only source judge must
not be trained to infer an unseen graph to satisfy a label. Separately, ten
decisive old/new label differences and three unresolved source judgments in
one question require an aligned evaluation/control contract. They are not
evidence that all historical selector errors were annotation errors.

## Recommended bounded next step

Approve one **public-only, offline input/control preparation**, using the same
four cached, hash-verified calibration PDFs. Keep source-only navigation,
one query embedding and at most one prospective source-ID judgment; it may
return only issued IDs and closed status/verdict enums. Display remains 0–3
unverified original-PDF links, with no weak filler or generated answer.

1. Build a separately versioned inert packet containing the exact current
   question, existing page text/cue and a faithful full-page raster for each
   of its four candidates. Apply this representation uniformly, not just to
   the five known failures. Bind every raster to source SHA, physical page,
   render parameters and raster SHA. Preserve the original packet unchanged.
2. Use the same educational rubric for the prospective selector and scorer:
   the page teaches the requested relation or an explicitly connected concrete
   learning step; the cue locates that material and need not contain a complete
   answer. The page image is evidence, never an instruction. Strict local ID
   parsing and current-source provenance remain independent of semantic judgment.
3. Keep all 66 cases and the sealed tri-state labels. Design an explicit
   uncertainty/clarification control for the unresolved question: no primary
   reference or claim of corpus-wide absence may be justified by `Unsure`.
   It must remain separately reported and must not be converted to a successful
   binary no-match. Preregister how it counts before a future model score.
   If an additional conclusive no-match control is necessary to preserve the
   existing minimum, retain the uncertain case and add at most **one** independently
   reviewed public four-page control; do not replace the difficult case.
4. Verify raster readability and evidence representation at the actual intended
   input resolution. Use the five diagnosed gaps and a frozen sample of 16
   agreed weak pairs as development-only feasibility controls. Two fresh
   reviewer contexts may inspect these prospective inputs without model choices
   or old labels. Record uncertainties rather than forcing positive labels.
   This is an input check, not an independent model/quality validation.
5. Implement only mock payload/parser, image/source binding and failure controls;
   freeze the proposed wire and measurement contract before any trial. Do not
   open the existing 60-case heldout; first document how a future independent
   annotation will make its review contract compatible. Do not alter the old
   labels, historical scores or any consumed ledger.

## Offline limits and stopping rules

- Only four existing public calibration PDFs and their **80 distinct cited
  pages**; no PDF/model downloads, private Knowledge, root environment/key
  inspection, database or runtime edit. Generated public artifacts stay Temp.
- At most four images in an inert request; full physical pages, no semantic
  editing, invented OCR description or selective crop. Proposed render caps:
  1,600 pixels on the long side, 2 megapixels and 1 MiB encoded per page;
  6 MiB assembled request. Keep native context/cues and exact metadata.
  Reject unreadable/oversized output rather than silently reducing detail.
  These are proposed offline bounds to measure, not an approved online budget.
- Bounded local rendering/preflight: at most 4 CPU, 2 GiB additional RAM,
  30 seconds per child and 600 seconds total per preparation stage. Keep
  source/raster fingerprints and content-free size/timing/failure results.
- **Zero Gemini requests**, token-count API requests, application-model
  inference, File API uploads or private transfers. No Ask activation or
  canonical schema/model-policy change. A future provider trial requires a
  fresh endpoint/model/price/calls/image/token/time/cost envelope, including
  image tokens and failed-call uncertainty.
- Stop if the actual bounded images do not represent the missing relations,
  weaken the weak-source controls, exceed bounds, or leave a defensible control
  contract unresolved. Do not continue another prompt sweep or count this
  input preparation as a release pass.

Keep all existing hit/per-form, exact-cardinality, no-match, ≥90% all-displayed
usefulness, availability, privacy/access and release gates. No larger model,
extra embedding or lower quality threshold is proposed here. A production
visual path would additionally require an approved isolated renderer,
dependency/license/runtime review, immutable policy/migration and separate
private-page-image disclosure; this offline preparation does not authorize it.

## Verified public API feasibility, not a live test

The official [Gemini 3.5 Flash-Lite model documentation](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite)
lists image input, structured output and thinking support. The
[generateContent reference](https://ai.google.dev/api/generate-content)
documents image-and-text input, while
[image understanding](https://ai.google.dev/gemini-api/docs/image-understanding)
documents inline image data. The [token guide](https://ai.google.dev/gemini-api/docs/tokens)
confirms that images contribute input tokens; image byte bounds are not token
or price bounds. These pages were checked on 2026-10-01. They establish an API
representation option, not source-selection accuracy, free-tier availability,
runtime authorization or an actual request. The dormant application policy
still targets its pinned 3.8 model and remains disabled.
