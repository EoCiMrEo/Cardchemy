## Decision

### Candidate and output contract

Keep at most one `QUESTION_ANSWERING` embedding of the current question per
durable attempt. Use the existing Subject-authorized exact-vector/FTS
candidate paths and bounded same-page/neighbor inspection; keep ownership or
enrollment, selected document, reviewed publication, readiness, current
revision/corpus and active embedding-space filters inside SQL. Measure
candidate recall separately from final page selection. Do not introduce
two or three query vectors without an independent candidate-recall miss and
a further approved policy.

If there are eligible candidates, a separately bounded Gemini request may
receive only the **current question** and a server-built list of currently
authorized candidate pages: opaque per-attempt candidate IDs, exact extracted
cue, bounded page/heading context and physical page association. No prior
chat, user profile, other Subject, unselected document, unpublished revision,
raw PDF bytes, credential or answer draft is sent. The request asks which
zero to three pages are useful for reading this question and returns only an
ordered array of those candidate IDs. It may choose fewer than three or none;
the server never fills a slot with a weaker page. It must not produce learner
answer text, quotes, claims, citations, reasoning or confidence labels.
The direct Gemini request explicitly sets `store=false`, disables redirects
and uses no automatic HTTP retry. The public pilot and prospective worker use
the same bounded REST body for the source-ID decision; differences in local
candidate assembly still require separate private release measurements. This
request setting does not override Google's abuse-monitoring retention terms.
Local follow-up resolution may guide candidate retrieval, but neither a
prior question nor a derived antecedent/entity is silently sent to Gemini.
If the original current question and selected pages cannot support a useful
judgment, request clarification. Any later derived-entity transfer needs a
separate operator decision and disclosure.

The server validates the complete structured response against the issued
ephemeral ID set, count and uniqueness; malformed, foreign or ambiguous
output fails safely. It derives every title, exact contiguous cue, offset,
current revision and original-PDF page link locally from canonical Knowledge,
then atomically commits at most three job-owned references. The model cannot
write a citation or upgrade a page to verified evidence. At commit and at
every reference/PDF read, reauthorize and revalidate the **entire** bundle;
one invalid member hides it all. User-visible copy always says the pages are
related published material **not verified answers**. A legitimate empty
selection is distinct from provider unavailability, invalid output,
unresolved follow-up and a retrieval failure. An unresolved referent prompts
clarification without transferring private history. The independent lecture
browse/search remains available while Ask is off or cannot select pages.

The new `related_knowledge_navigation_v4` policy is immutable and versioned,
with admission, retry, stage and
cost accounting fenced from old answer policies and navigation-v3 jobs. It
makes **at most one query-embedding request and at most one source-ID judgment
request** per attempt, with zero answer-generation and answer-verification
requests and no automatic retry after uncertain execution. No rank call is
made when an ambiguous question or empty authorized pool can be resolved
locally. An embedding outage may use the already approved bounded lexical
candidate path, but its source-judgment behavior and no-match reporting need
separate measured coverage; a judge outage cannot be mislabeled as a true
no-useful-source result. Provider admission, price/cost estimate, disclosure,
telemetry and manual retry consent must account for both possible physical
requests. Logs retain safe stage/reason/usage counts, never question text,
candidate text, provider response, raw IDs or secrets.

## Rationale

One semantic source judge targets the measured page-selection/no-match gap
while retaining the pedagogical source-only experience. Restricting model
output to issued IDs and deriving the references locally prevents a remote
response from becoming a citation authority. A public-first pilot tests the
new privacy/cost boundary without transferring the owner's private lectures.
This approach is a hypothesis, not a guarantee that arbitrary questions
will yield useful pages or that the selected model will meet the gate.

## Consequences

- The dormant application now has an immutable v4 policy, typed
  capability/disclosure, bounded judge adapter, stage and physical-call
  accounting, fail-safe structured-output handling, and the `0029` Alembic
  revision for v4 job, `source_judgment` stage, result and reference-policy
  constraints. Negative provider/authorization/race tests and independent
  release checks must pass before activation. Existing v3 jobs remain readable
  without being reinterpreted or retried under the new policy. The judge's
  provider/model/cost snapshot is independent of retired answer fields.
- Source text egress must be disclosed before asking, even though the
  learner sees no generated answer. Operators must review current provider
  terms, region, logging and retention. A configured key alone is neither
  authorization to spend nor evidence of privacy or quality.
- The prior three local one-shot audits remain failed historical evidence.
  Their consumed ledgers and calibration data cannot be recycled as a new
  independent quality pass. Ask and all four open Lane 6 checklist items
  remain gated.
